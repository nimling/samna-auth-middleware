# v3: claimius as a PostgreSQL extension that governs access inside the database

This plan is the handoff for the session that builds `v3`. It carries the intent, the facts verified against the code and the platform at `v2.0.0`, and the work in order. Nothing in it is built yet.

## 1. The intent

1. Claimius ships as a PostgreSQL extension: `CREATE EXTENSION claimius` installs the protected `claimius` schema, and an upgrade is `ALTER EXTENSION claimius UPDATE`.

2. Token and access move into SQL. The database verifies the token, resolves the actor, and computes secrets and credential digests itself. The Go access layer the middleware carries today is removed, and every connecting part authenticates through the database.

3. Every table registered in a consumer schema is access checked against the `claimius` schema by the database itself, on every read and every write, whoever connects.

4. Existing database principals are actors too. On an Azure configured PostgreSQL an Entra ID login is resolved to its claimius user, the same way a token is, so a person or a managed identity connecting directly is governed by the same claims.

5. Claimius exposes helper functions for consumer migrations. A migration creates claimius service accounts that may run only migrations, or only migrations of named structures, and what an account may create, alter or drop is granted as a claim.

6. The custom scope on a claim gains a database meaning. Claimius ships the functions that parse a scope and apply it to the database: who may create which structures in which schema, and which rows and fields a scope reaches.

7. All of it is generalized into claimius methods that cover every way data is accessed or changed, so the whole system is governed from the database.

8. A scope used to control a resource outside the database stays as it is. It is immutable within the process that received it from claimius, so an outside consumer keeps reading it through `ScopeAccess`.

9. Each root organization marked for separate billing is its own partition. The organization type marks it.

## 2. Facts verified at v2.0.0

10. The schema ships as smig base sets, `prophet/database` and `disciple/database`, pulled by a git include at a pinned ref. The only extension it needs is `pgcrypto`, created in the `pre` step of each `migrate.yml`.

11. There is no row level security and no event trigger anywhere in either set. Access is enforced by the `claimius_reader` role and the `get_*` functions, and the rows of a registered table are reachable by any role holding SELECT on it.

12. Tokens are signed RS256 by samna_auth, with one HS256 site. `dpop/dpop.go` accepts RS256, PS256 and ES256. `pgcrypto` has HMAC but no RSA or ECDSA verification, and `pgjwt` is HS256, HS384 and HS512 only, so neither verifies the tokens in use.

13. `claimius.organization.type` is `VARCHAR(50)`, free text, and no SQL function reads it. Nothing marks a root as a billing unit today.

14. Azure Database for PostgreSQL Flexible Server installs only extensions on its allowlist, set through `azure.extensions`. It carries no `pg_tle` and no way to install a customer defined extension, so `CREATE EXTENSION claimius` cannot run there.

15. The Flexible Server admin is `azure_pg_admin`, not a superuser. Upstream, only a superuser creates an event trigger. Whether a PostgreSQL 17 `login` event trigger or a `ddl_command_start` trigger can be created there is not documented and is tested on a tst server before anything depends on it.

16. Flexible Server authenticates Entra ID principals natively and maps each to a database role through `pgaadauth`, so `session_user` is the Entra principal's role on a connection made that way.

## 3. What has to be decided before code

17. The packaging. A real extension installs on a self hosted or AKS PostgreSQL only. On Flexible Server the same objects ship as the smig base set, or the platform changes. Both targets from one source is the default until decided otherwise.

18. Where a token is verified. RS256 and ES256 verification in the database needs a C extension or `plv8`, and neither is on the Flexible Server allowlist as a customer build. The alternatives are an HS256 token minted per session for the database, or an Entra ID login as the only direct path.

19. How a session carries its actor. A transaction local setting set once per transaction and read by every check, a login event trigger, or the connecting role itself. Row level security reads it on every row, so the per row cost is counted in rows and index entries in `.nimpress/claimius/` before the choice.

20. How row level security meets the read time settle. A policy runs inside SELECT and on a replica, where the settle cannot write. The policy reads `user_object` and the open areas of `access_diff` as they stand, and the settle stays with the `get_*` entry points and the drain.

21. What a billing partition is. List partitioning of `user_object`, `claim_object`, `user_claim`, `audit` and the registered tables on `sa_root_id`, with the root organization's type as the marker, and the value set of `organization.type` fixed first.

22. Which part of the middleware remains. The `/sam` sync, federation and the typescript package serve outside processes and may stay; the Go access calls go.

## 4. The work, in order

23. The proofs first. Row level security, the session actor and partitioning are written into `.nimpress/claimius/` as counts, per check and per listing, against `v2.0.0`, before any code.

24. The tst checks from 15 and 18: event trigger creation as `azure_pg_admin`, and the allowlist on the Flexible Server version in use.

25. The extension packaging: a control file, one install script per version built from the base set, and the upgrade scripts between them, with `pg_extension_config_dump` on every table holding data.

26. The session actor and token verification in SQL, with secrets and credential digests computed in the database.

27. Row level security on every registered table, written by `init_claimius_tables`.

28. The migration service accounts and the scope functions for structures, gated by the event trigger or by the grant functions if the trigger is refused.

29. Billing partitions on the marked roots.

30. The Go access layer removed from the middleware and from each consumer, nimployer, bookable_server_test and samna_auth, each tested on its own and against the database.

31. The `v3` changelog in `.nimpress/changelog/`.
