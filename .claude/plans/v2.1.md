# v2.1.0: settle ahead of the read when the database has room

This plan is the handoff for the session that builds `v2.1.0`. It carries the case that starts it, the facts at `v2.0.0`, the feature, the math that decides it, and the work in order. Nothing in it is built yet.

## 1. The case

1. On a database that was just seeded, or just took a snapshot, no user holds a single `user_object` row, and every row the seed wrote left an open area in `claimius.access_diff`. nimployer's debug seed leaves 16,086.

2. The first listing of each user pays for all of it: `get_claims`, `get_objects` and the other listings settle that user's share of every open area they need before they read. On nimployer at `32f6acd` the first `get_claims` of the seeded user takes 15.2 s, the second 0.11 s. At `1604698` the first took 1:59 and ran into the 120 s read timeout.

3. The work is the same whoever does it and whenever. Done by the read, the user waits for it; done ahead, while the database has nothing else to do, nobody waits.

## 2. Facts at v2.0.0

4. `claimius.drain_access_diff(p_limit_pairs)` settles shares ahead of the read. It takes a share only where the holder reads more often than the area is raised, `now − sa_created_at ≥ raise_count × (now − last_used_at)`, and only for a holder with a `claimius.user_activity` row. A user who has never read has no row, so the drain never touches the users of a fresh seed.

5. The drain runs from the disciple sync loop, `disciple/sam/main.go:282`, every `drainInterval` on the one process holding the sync lock, `drainPairs = 1000` shares a call, through `shared/access.go:278` `PostAccessDiffDrain`. It runs whether or not the database is busy. A prophet does not run it.

6. `user_activity` holds one row per user, `last_used_at`, written by `touch_object_usage`. It carries no read rate, no count and no history.

7. A share is settled per area: batches of 128 areas, one recompute per object type a batch, `_settle_diff_share` in `V2.2__claimius_functions_internal.sql`. A user with nothing materialized pays one batch per 128 areas even when a single pass over everything the user reaches would cost less.

8. Every lock a settle waits for is capped at `_settle_lock_timeout()`, so work ahead of a read cannot hold a writer or a reader for longer than that.

## 3. The feature

9. A cold user is built whole. A user whose share holds more open areas than objects it can reach is settled by one recompute per object type over everything its claims reach, and every open area it holds is recorded settled at its `raise_count` in one statement. The choice is made from counts the database has, per user, before any work.

10. Idle is measured, not assumed. The prewarm runs only while the database has room: the other backends working on the database, `pg_stat_activity` rows in state `active` other than its own, are below a threshold, and the process's own request rate is below one. It yields as soon as either rises, between batches, and never waits on a lock longer than `_settle_lock_timeout()`.

11. Who comes first is predicted. The next read of each user is estimated from what the database records of that user, and the users whose next read is soonest are settled first. A user who has never read but can log in, one with a live grant in the app, ranks by the time since its grant was written, so the users a seed or an onboarding just made come first.

12. The prewarm is the drain grown up: one entry point, one loop, on the process that already holds the sync lock on a disciple, and on the prophet for its own system app and for apps no disciple serves, the areas `drain_access_diff` already assigns to the prophet.

13. Nothing about correctness changes. A read still settles whatever is still open when it arrives. The prewarm only moves work from the read to a moment before it.

## 4. The math that decides it

14. With `A_u` the open areas user `u` holds, `S(a, u)` the objects of area `a` that `u` can reach, `R_u` the objects `u` reaches, `c_b` the fixed cost of one recompute call and `c_o` the cost per object recomputed:

```
area settle   = ⌈A_u / 128⌉ · T · c_b + Σ_a |S(a, u)| · c_o      T object types a batch
whole build   = T_u · c_b + |R_u| · c_o                            T_u object types u reaches
build whole when  |R_u| + T_u · c_b / c_o  <  Σ_a |S(a, u)| + ⌈A_u / 128⌉ · T · c_b / c_o
```

15. Measured at `32f6acd`, one user over 16,003 open areas: 126 batches, `recompute_user_object` 138 calls, 2.2 s in total. `c_b` and `c_o` are fitted from `pg_stat_user_functions` on the bench in `.nimpress/claimius/materialization.md`, and the rule is proven there in counts before code, the way every other rule in that page is.

16. The prediction is a rate, not a model. With `n_u` reads of `u` counted in a window of length `W` and `t_u` the time since its last read, the expected wait to its next read is `W / n_u − t_u`, floored at 0. The prewarm takes users in ascending order of that wait, and a share is worth settling ahead while the user's rate `n_u / W` is at least the area's raise rate `raise_count / (now − sa_created_at)`, the drain's test from point 4 with a rate in place of one timestamp.

17. The idle budget is bounded. A prewarm pass settles at most `P` shares and stops when the active backend count reaches `k`. With `c_s` the mean cost of a share, one pass holds at most one connection for `P · c_s`, and the section 3 inequality of `.claude/rules/pool.md` does not change, since the pass runs on a connection the sync loop already holds.

## 5. What has to be decided before code

18. What `user_activity` carries for the rate: a read count per window beside `last_used_at`, written by `touch_object_usage`, which already batches every use per flush. One integer column and one window start, no history table.

19. The thresholds `k` and `P`, and the pause between passes. The defaults come from the measurements in 15 and the pool budget in `pool.md`, and are constants in SQL like `_object_lock_budget`, not configuration.

20. Whether the prewarm takes users with no read at all on the prophet, where every app lives, or only on the database that serves the app.

21. Whether `drain_access_diff` keeps its name. The feature replaces it, so either it keeps the name and grows, or it is renamed everywhere with no alias; there is no second function beside it.

## 6. The work, in order

22. The math first: the cost rule of 14 and the rate of 16 written into `.nimpress/claimius/materialization.md`, fitted on the bench.

23. The whole build in SQL, the choice of 9 inside `_settle_diff_share`, so a read gets it too, not only the prewarm.

24. The rate in `user_activity` and its write in `touch_object_usage`.

25. The prewarm in `drain_access_diff`: the idle test, the ordering, the budget, the yield.

26. The Go loop: the disciple sync loop and a prophet loop call it on the process holding the sync lock; the fixed `drainInterval` becomes a pause that shortens while passes find work and the database is idle.

27. pgTAP tests per role: a cold user built whole equals the same user settled area by area, pair for pair; a prewarm pass settles nothing while the active backend count is at the threshold; the order follows the predicted wait. A Go `dbtest` for the loop.

28. The measurement on nimployer's fresh seed: the first `get_claims` after a prewarm pass, against 15.2 s at `32f6acd`.

29. The `v2.1.0` changelog in `.nimpress/changelog/`.
