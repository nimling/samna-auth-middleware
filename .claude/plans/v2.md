# v2.0.0: one middleware from the nimployer line and the bookable line

This plan is the handoff for the session that builds `v2.0.0`. It carries the system as it is meant to work, the task, the starting points, the test protocol, the smig work, and every correction given during the failed attempts. The work is done in agents as much as possible; the session coordinates and verifies.

## 1. The system

1. One middleware, two roles. The prophet is samna_auth, the authority that holds every app and serves `/sam`. A disciple is a product service (nimployer, bookable) holding one app's copy of the shared rows in its own Postgres and answering every access question locally, with no call to samna_auth per request.

2. The shared types are claimius's own: organization, location, claim, claim_object, user_claim, samna_user, samna_client, samna_secret, user_relation. The middleware knows these and nothing else. It never names a consumer table, column or type, has no `public.*` default, and no consumer filter in a shared function.

3. Prophet and disciple each own their own tables and types. samna_auth owns app, provider, module, monitor and so on. bookable owns bookable, checkin, action and so on. Each registers its tables with `init_claimius_tables`, its own claimius computes access for them locally, and its own SQL wraps `claimius.search` and the graph functions for its own shapes.

4. Grants live on the prophet. A disciple sends writes to the shared types there through `sdb.NewInsert`, `NewUpdate` and `NewDelete` with `.Access(ac)`, and pulls everything back with `sam.SyncStart`. A grant may point at a consumer's own row. Its `object_type` and `object_id` travel opaque, and the disciple computes access for its own table when the grant arrives by sync. Both original lines routed writes this way.

5. The disciple schema has no `app_id` and no `app_object`; the prophet has both. Scoping is written on the prophet side only. The disciple bootstraps with `claimius.init()` and receives its schema as a smig git include of `disciple/database` at the pinned ref. After the upgrade no `prophet` or `disciple` folder and no claimius migration file exists on a consumer's disk: smig downloads the role folder at the ref, and the middleware ships base sets only, with no `migrations/` folder under either role. The upgrade a host needs to reach that schema from the version it runs is that host's own migration, `V2.0.0__claimius_unified.sql` in its own `database/migrations/`, not a migration in the middleware.

6. A consumer maps its own types with the middleware's helpers: `sdb.StripObjectSchema`, `sdb.ResolveObjectType`, the model's table tag, `init_claimius_tables`. If it maps, its objects flow through the standard path. If it does not, nothing happens. The `/sam` channel is only reached by the middleware; the sauth CLI never touches it.

7. Sync is one protocol, pull. The prophet trims events by the disciples' cursors. The 1.0 push sender in samna_auth and the prophet's `POST /sam/sync` receiver have no place left.

8. A machine client is an actor. `samna_client.client_id` is its `user_id`, it has a per-app `samna_user` row of type `client`, and its grants sit on that id. The seeded clients on tst, `nimio` and `samna-sync`, have that shape. samna_auth's `POST /api/client` and `POST /api/client/:id/claim` did not produce it: the grant landed on the row id and no actor row was made.

## 7. smig SQL testing, run as an agent

29. Build into `samna/migrate` a modern way to write and run SQL tests, on an open standard from GitHub. pgTAP is the one to build on: TAP output, `plan`, `ok`, `is`, `throws_ok`, `results_eq`, `pg_prove` compatible.

30. The runner starts a throwaway Postgres, applies a `migrate.yml` fresh and upgraded from a chosen tag, runs `test/sql/**` inside transactions that roll back, reports TAP, and offers helpers to scaffold a test and to assert a function's rows. `just test` wires to it. It extends smig in place; no sibling tool.

30.1. The middleware tests its own two role folders with that runner, through a `migrate.yml` beside each set, fresh and upgraded from a tag. No testing logic is added to a consumer for the move, and a consumer that wants SQL tests gets them the same way, with `tests:` in its own `migrate.yml`.
