# How a consumer connects

1. A disciple binds to one prophet through `SAUTH_ENDPOINT` in its own environment, and is the only part of a service that reaches it: `../.claude/rules/platform.md` Prophet and disciples.
2. `SAUTH_APP_SLUG` and `SAUTH_APP_SECRET` name the app; the app and its secret come from the workspace `apps` skill, never a seed. `SAUTH_REDIRECT_URI` and `SAUTH_PAGE_REDIRECT` are the root app's login return. An Initiate app of the root, another frontend on its own origin, logs in through `/api/auth/<slug>/login` with `redirect_uri=<SAUTH_REDIRECT_URI>?app=<slug>` registered on it, and returns to its first redirect URI; logout is `/api/auth/<slug>/logout`. Its registered callback, `cookie_domain`, `cookie_same_site` and origins come from samna_auth; a host mounts `smw.InitiateMiddleware` and uses `smw.GetOriginAllowed` for CORS. The disciple reads the Initiate apps from `GET /sam/app/initiate` and holds them in memory.
3. `PG*` is the consumer's own database holding its replicated `claimius`; `SAUTH_REPLICA_DSN` an optional read replica.
4. Sync is pull only: `sam.Init` reads `/sam/sync/:cursor` from the prophet. One puller per database. `sam.Init` also fetches the app's own `private_seed` from `/sam/app` and holds it in memory only, for `SamnaSecret.Resolve`; the prophet stores it wrapped under `SAUTH_MASTER_KEY`.
5. `SAUTH_DEBUG_USER_ID` and `SAUTH_DEBUG_CLIENTS` turn on debug mode, which skips the sync and acts as the debug user; `SAUTH_DEBUG_INITIATE_APPS=<slug>=<origin>,...` stands in for the Initiate apps there. Set only in a local `.env`.
6. `SAUTH_CLIENT_ID` and `SAUTH_CLIENT_SECRET` are the consumer's machine client for service to service calls. A cli's machine client sends its pair as Basic auth to the service, which `smw.UserAuthMiddleware` checks against the replicated `samna_client`.
7. Cli login: a cli opens the service's own `/api/auth/login` with its `cli_challenge`, and `cli_redirect` with `cli_state` for a loopback or neither to paste; `GetCallback` hands the code to the cli without exchanging it. `sam.RegisterCli(e.Group("/api/auth"))` mounts `POST /api/auth/cli/token` (the `authorization_code` grant with the cli's `code_verifier`, and `refresh_token`) and `POST /api/auth/cli/revoke`, rate limited, forwarding to the prophet's `/oauth/token` and `/oauth/revoke` with `SAUTH_APP_SLUG` and `SAUTH_APP_SECRET`. The disciple stores nothing of a cli login, and a host carries no cli login handler or table of its own.
8. Telemetry: the host calls `nimtel.Init` and mounts `smw.TelemetryMiddleware()` before the auth middleware; the Container Apps env supplies `OTEL_EXPORTER_OTLP_*`.
9. Consumers on v2: samna_auth (prophet), bookable_server, nimployer, samna-sync, samna_connect, samna_sign, hvergel, samna-developer. `bookable_server` and `samna.io` stay on v1. `../.claude/scripts/repos.sh` prints every pin.
10. Access codes and guests: `smw.UserAuthMiddleware` resolves `samk`, `SAuth-Code` or the `__Host-sauth_samk` cookie on every route, and a route group with `smw.UserAuthOptions{Guest: true}` serves an open guest claim to a request with no credential. Codes and guest modes are written on the prophet through `/sam/code` and `/sam/claim/:id/guest`; the design is `.nimpress/claimius/users.md`, Guests, Access codes and The guard.
11. Runners: a host makes one context in `main` with `signal.NotifyContext` and starts every runner on it with `Init(ctx) error`, fatal on error: `sam.Init` (disciple), `sam.PeerInit` (a prophet mirroring a peer), `notification.Init` (either role), `analytics.Init` (prophet), `uptime.Init(ctx, logger, opts)`. None takes a database; each reads the pool `shared.Connect` recorded, through `shared.Instance`, which `sdb.Instance` is on both roles. The disciple's asset options are `shared.Options` on that one `*shared.DB`, set by `sdb.Init`. On the signal the host shuts the http server down, waits on every `Done()` and closes `sdb.Instance()` last. There is no `Stop`. `.nimpress/disciple.md` Lifecycle.
