## One middleware for every consumer

Nimployer ran the 1.1 line and Bookable ran the 1.0 line on a copy of its own. Version 2 is the one middleware both run, prophet and disciple alike, under the module path `github.com/nimling/samna-auth-middleware/v2`: Go accepts a v2 tag only for a path ending in `/v2`, so every import moves from `github.com/nimling/samna-auth-middleware/...` to `github.com/nimling/samna-auth-middleware/v2/...`.

- The middleware carries the shared types only: users, organizations, locations, claims, grants, bindings, clients, secrets, fields and relations. Bookable's own names left the middleware and live in Bookable.
- The graph window and object usage were taken out of the Go layer while the lines merged, and came back below as generic claimius features every consumer shares.
- The schema ships as two base sets, one per role, and nothing else: the middleware carries no migrations. A consumer that must drop objects of its own made for the earlier line, such as the push sync trigger or its own usage and graph functions, does it in its own `V2.0.0__claimius_unified.sql`; the base sets bring the claimius tables to the new shape themselves.
- The SQL tests are pgTAP files run per role by `smig test`, against a fresh database and against one migrated from the last tag.
- The prophet no longer accepts pushed access rows: sync is pull only.
- One object type resolver, `ResolveObjectType`, serves both roles, and a disciple's own object types resolve on the prophet.

### Fixes kept from both lines

| Fix | Effect |
|---|---|
| Creator stamping | A routed model whose creator fields are pointers is stamped with the actor's grant |
| Grant updates | `PATCH` and `DELETE` on a grant address it by claim and member within the calling app |
| Ancestor walk | The walk to the closest grant honours `inherits`, denies and the claim mask |
| Forwarded identity | The owner of every forwarded token is checked, and only one identity is accepted |
| Location and relation updates | The prophet answers `PATCH` on both, the verb a disciple sends |
| Sync scope | The feed carries only the organizations and locations linked to the app through `app_object` |
| Absent tables | Access and search settle where a bound table is absent from the database |
| Settle under a lock | A batch of open access changes that meets a lock settles one change at a time, so a new reader's own grant is never held back by an unrelated locked change |
| One read settles everything | A listing settles every open change it needs in one read, however many pairs they move, and takes no lock per object: it holds one advisory lock, its share lock, and the row locks of what it changes. Who sees whom is no longer counted inside the write that moves a pair, which needed every other holder of the object and a lock per object until commit, but recorded as one `user_users_diff` row and folded by the reads that need it, exact for their snapshot. Usage flushes record `usage_diff` rows instead of updating pairs a read may hold. Over 16,000 new organizations one listing returns all 16,001 in 1.9 seconds where `v2.0.0-alpha0023` took 32 listings, the first returning 513; a writer beside a reader in its transaction completes in 2 to 3 ms, a usage flush on a pair the reader holds in 3 ms instead of waiting for the reader, 3,005 ms; `_lock_objects`, `_object_lock_budget`, `_count_user_users`, `_refresh_user_users` and `_lock_all_objects` are dropped |
| Claim update | `PUT` and `PATCH /sam/claim/:id` store every field sent, `name`, `description` and `type` with `access`, `inherits` or `level`, and refuse an invalid `type` |
| Auth path | The login redirect sits beside `SAUTH_REDIRECT_URI`, so a consumer mounts the auth routes where its redirect URI says; the BFF base path and the browser session default to `/api/auth` |
| User delete | `DELETE /sam/user/:id` answers the deleted user, the row a routed delete reads, instead of an empty list |
| Routed record | A routed update or delete takes its record from the model, never from a `Where` expression, and is refused with `ErrRoutedNoRecord` when the model carries none; `samna_user` and `samna_client` models carry theirs |
| Routed `Set` | A routed update carrying a `Set` expression is refused with `ErrRoutedSet` instead of being sent without it |
| Root organization | A root organization keeps the id it was given, and `POST /sam/organization` without `owner_id`, or with `owner_id` equal to its id, creates one linked to the calling app |
| Actor on create | `POST /sam/organization` and `POST /sam/location` answer `400` without `created_by` |
| Held and visible claims | `get_claims` lists the claims the user holds through a live grant; the claims the user can see or manage, held or reached through a cascade, across apps on the prophet, are `get_objects` of `claimius.claim`, and `ClaimWhere` and `GetClaims` take both |
| One write builder | Every write goes through `shared`'s builder, which sends it to the prophet when the disciple's `Init` turned routing on and runs the claimius function otherwise; the write helpers, `CreateVirtualClaim`, `DeleteUser`, `CreateOrganizationUser`, `IssueUserToken` and `UpsertUserExternal` included, sit on it, and the disciple's own builder and its copies of three helpers are gone |
| One organization user | `insert_organization_user` takes the app on the prophet, an identity that reuses the user its `user_token` names and writes the token, the grant reason, and answers `created`; `/sam/user` with `owner_id`, `/sam/user/token` and `/sam/user/external` call it with the payload's `created_by` and answer `400` without one, and `Created()` on the insert reads `201` or the function |
| Function names | Every write function is named for the row it writes: `insert_` creates and refuses a duplicate, `upsert_` creates or returns the existing row, `update_` and `delete_` change and soft delete. `create_claim`, `assign_claim_object`, `assign_claim_user` and their `remove_` and `update_` forms are `insert_claim`, `insert_claim_object`, `insert_user_claim`, `delete_*` and `update_user_claim`; `ensure_app_user`, `ensure_app_client`, `create_app`, `create_root_organization`, `link_app_object`, `link_app_organization` and `unlink_app_object` are `upsert_app_user`, `upsert_app_client`, `upsert_app`, `upsert_root_organization`, `upsert_app_object`, `upsert_app_organization` and `delete_app_object`; `create_organization_user` is `insert_organization_user`; `offer_handover` and `accept_handover` are `insert_app_handover` and `update_app_handover`; `write_audit` and `ensure_audit_partition` are `insert_audit` and `upsert_audit_partition`; `post_consent` and the `post_analytics_` writers are `insert_consent`, `insert_analytics_events`, `upsert_analytics_session`, `upsert_analytics_heat` and `upsert_analytics_capture`; the bootstrap `init` is `upsert_system_app` on the prophet and `upsert_disciple_state` on the disciple, `init_disciple` is `upsert_disciple_state`, `init_hybrid` is `upsert_prophet_peer`, and `init_claimius_tables` and `init_claimius_internal` are `upsert_table_info` and `upsert_internal_table_info`. The old names are dropped |
| Secret binding | `insert_secret` stores a secret and binds it to the claim of the actor in `sa_created_by` with owner, write and read; `POST /sam/secret` calls it and answers `400` without `created_by`, and a debug disciple calls it locally, so every secret is reached through `get_secrets` on the prophet and on every disciple of the app |
| Organization seed | `organization.private_seed`, the key of its apps' `app_secret`, reaches peer prophets only: `get_sync_events` drops it from organization payloads for a disciple and the snapshot no longer marshals it |
| Peer grant | A home serves an app as a peer only to a pull presenting the secret of a live `peer_grant`: `upsert_peer_grant` stores its SHA-256, the mirror keeps it in `prophet_peer.peer_secret`, which `upsert_prophet_peer` takes as `p_upstream_peer_secret`, and sends it in `SAuth-Peer-Secret`; without one `?peer=true` answers `403`, so the app credential its disciples hold no longer opens the app keys and organization seeds |
| Guests | `POST /sam/guest` makes the guest in the calling app through `upsert_guest_user`, as a `samna_user` of type `guest` holding the claim under the actor's owning grant, and signs its token with the calling app's key; it answers `404` for a claim outside the app and `403` for an actor that does not own it |
| Claim levels | `claim.level`, from 0, orders denies before classes: a deny subtracts from every grant below its level whatever their classes, at the same level the direct and tree classes decide, and a link takes the higher level of its two claims, whose claim decides its bits. `insert_claim` and `update_claim` take `p_level`, every access row and `AccessClaim` carry the level of their grant, and level 0 everywhere resolves as before |
| Level checks | Binding a claim above level 0, deny or grant, needs the actor to hold that level on the object; granting such a claim or raising its level needs write on the claim and lifts no lower deny the actor faces on what it reaches; every refusal of these write checks, levels, held masks and links alike, raises SQLSTATE `P0403`, which a handler answers with `403` |
| Verify | `just verify` builds a prophet and a disciple from the tree and checks that both answer every user of one scenario the same, levels included, after the snapshot and after the feed; `just test` runs it as well |
| Refusals end to end | The prophet's claim, binding and grant handlers answer `P0403` with `403` through `errorsx.ErrToHttpCode`, which reads the SQLSTATE, and the write builder returns `ErrNoAccess` for a routed write the prophet refuses and for a local write the database refuses, so a consumer answers `403` from one sentinel; `PUT /sam/claim` sets the access sent under its JSON key `access`; a routed write the prophet answers `404` and a local one the database refuses with `P0404` return `ErrNotFound` |
| Snapshot order | The disciple snapshot sends organizations and locations parents first, by `sa_level` then `id`, so a child never applies before its parent and keeps the inherited grants and denies of its ancestors |
| Duplicate pairs | The upgrade keeps the newest of any duplicated `user_object` pair before the pair becomes the primary key |
| Record ids | Updates and deletes take the record id from the model for every routed type |
| Debug disciple | A debug disciple takes its app seed from `SAUTH_DEBUG_PRIVATE_SEED` |
| Unknown user | An unknown user answers `404` instead of `403` |
| User image | `user_image` is gone |
| App identity | The prophet's functions resolve their app through `get_app_id` |
| No bypass | A settle that fails raises from the read that ran it: the check, the listing, the queue and the batch settle catch only a lock wait past the settle timeout and a deadlock, which leave their unit for the next read, and `_affected_users_for_object`, `_actor_user_for_row` and `in_replay_mode` swallow nothing. The write triggers no longer catch every error to write an audit row the raise rolled back, so a statement writing many rows opens no subtransaction per row: with 4 writers and 8 readers for 20 s a write averages 9.9 ms instead of 15.8, at most 98 ms instead of 164, and a listing 265 ms instead of 539, 826 ms at p99 instead of 1,955 |
| One user checked by key | `get_user_access` reads the one `user_users` row of the actor and the target by key and the pending rows of the two of them, and folds nothing, where it read the actor's whole visible set; the target resolves through an index on `external_id`. Bookable's user listing, one call per row of 200 users, reads 88,082,283 index entries instead of 437,835,068, 11.0 s instead of 17.3, the rest being the open changes of the first listing below |
| Bindings on a disciple's own rows | A binding on a row outside the `claimius` schema that the prophet holds nothing of is judged on the actor's access to the binding's owning organization, its type passed through untouched, so a disciple binds a claim on its own row through the prophet with `NewInsert().Model(&ClaimObject{...}).Access(ac)` |
| Claims rooted outside the app | On a disciple `claim.sa_root_id` and `claim_object.sa_root_id` carry no foreign key, so a claim owned by a linked organization whose root is not linked to the app applies from the snapshot and the feed instead of stopping both |
| Snapshot backoff | A snapshot that fails to apply waits out the doubling delay of a failed pull before the next one, instead of being pulled again every 100 ms |
| Graph links | `get_graph_links_owner` keeps each object's closest reached ancestor per tree with one window instead of an anti join that ran as a nested loop, 80 s a call on 99,066 edges; over 3,660 organizations it reads 21,821 index entries instead of 42,173. `_window_graph` and `_window_links` test against a hashed set |

## Access decided in fewer rows

Every change since the merge, grouped by concern, with what it saves.

### Checks and listings

- A check settles the one pair it asks about, and a listing settles only the reader's own share of each open change. Measured on one claim over four organizations held by three users: the first read settled 12 pairs before and settles 1 on a check now. A change nobody reads is never computed.
- A listing settles its open changes in batches of 128: one recompute per object type for the batch, one record statement and one clear, and the walk to inherited grants starts at the objects recomputed, not at the root above them. The first listing over 16,003 open changes, one claim bound on a root over 16,000 new organizations, took about 2 minutes one change at a time and takes 3.8 seconds.
- A listing of one type settles only the open changes that can reach that type, every one of them, oldest first, in one read, under one lock per reader however many it settles and however many pairs they move, so a revoke among thousands of open changes is settled before the listing reads and the listing never returns an object the reader no longer reaches. A settle gives up an area whose row it waits on longer than a twentieth of `deadlock_timeout`, leaves it open for the next read, and so never makes a writer the deadlock victim.
- A settle writes only the pairs whose value changed, so a check that settles an unchanged pair, or a listing over thousands of them, locks none of them. In a mixed run on one user, three readers, three writers and a usage flush, writes went from 1,436 to 2,934 in 30 seconds and their slowest from 213 ms to 81 ms, the slowest read from 3.5 seconds to 0.75.
- No settle and no write takes a lock per object, so the server's lock table holds one entry per reading transaction and at most 64 per drain. A drain holds the share locks of at most 64 users.
- `get_graph_links_owner` finds each object's nearest reached ancestor with a probe of the reader's pair instead of a join planned from a guess: 0.47 seconds instead of 66 for 48,009 links.
- Listings come from the reader's own index range, a page after the `after` id and at most `limit` rows in id order. A page of 50 among 5,000 reachable objects reads 50 index entries instead of 5,000, and sorts nothing. An unpaged listing keeps the order the handler gives it.
- Usage is counted on the pair a check succeeds on, per app, and flushed in the order the pairs are locked; a flush that meets a deadlock is retried, and a batch that fails is kept for the next flush. Search ranks by text match plus usage halved every 14 days, and a background drain settles open changes ahead of the reads of users who read more often than the change is raised.
- Registering a table with rows seeds its pairs grouped by user, one recompute per user and 1,000 objects, instead of one per pair: bookable's dev data, 46,063 objects over 210 users, registers in 92 seconds instead of 865, with 253 recompute calls instead of 57,082.
- The v1.1.9 table `object_usage` is retired on replay: its counts are added into the pairs that exist, each pair takes the later `last_used_at`, and the table is dropped, so a consumer carries no migration for it.
- Pure reads, such as capability matches and client lookups, go to a replica when `SAUTH_REPLICA_DSN` is set.

### Storage

- Access is stored once per user and object: the second table keyed from the object side is gone, and the reverse lookup is an index. A settled pair writes 2 index entries instead of 19, and takes about 805 bytes instead of about 1,316.
- The name, description, owner, location and search text of an object are stored once for the object, not once per user. A rename writes 1 row instead of one per user reaching the object.
- Organization and location trees are maintained incrementally: inserting a node writes its own ancestor rows instead of rebuilding its whole tenant tree twice, and moving a subtree rewrites that subtree only.
- `migrate_root` moves an object and its subtree under another root the same way, walking an organization through `sa_owner_id`, instead of rebuilding both tenants; the moved organizations join the new root's apps.
- Who shares an object with whom is kept like every other derived count: a pair entering or leaving writes one `user_users_diff` row and reads nothing, and the reads that show users fold the rows of their objects, each object by one fold that takes all its rows, and answer exactly as their snapshot holds the pairs. Holding the same claim no longer makes two users visible to each other.
- Usage is recorded the same way: a flush writes `usage_diff` rows and the user's next listing folds them into its pairs, so a flush never waits on a read and a read never waits on a flush.

### Grants and denies

**Breaking.** The effective access of a grant changed in four ways, and a consumer that relied on the old sums sees different masks.

| Rule | Before | Now |
|---|---|---|
| Binding mask | Added to the claim mask | Narrows the claim mask and never widens it |
| Denied mask | Bits removed independently | What remains is closed under implication: denying read also drops execute, write and owner |
| Composition | Reached the linked claim's bound objects only | Cascades from each binding like any grant, keeping the binding's position |
| Field scope | Scopes concatenated | Each field carries its own mask, and a deny can target single fields |

Capability grants follow the same rules: a matching deny subtracts, and what remains is closed.

### Sync

- The feed carries source records only, never derived access. Granting one claim to 50 users over 200 organizations sent 240,551 events before and sends 50 now.
- The cursor is a position `<txid>.<seq>` ordered by transaction, served only below the oldest running transaction, so a sequence that commits late is never passed over.
- A page applies in one transaction, and one process per database pulls: `N` replicas apply each event once instead of `N` times.
- Each disciple database keeps its own cursor on the prophet, and the outbox of an app is capped at its source records; a consumer further behind takes the snapshot.

### Security and audit

- Every read function runs as its owner under a pinned search path, so the reader role holds no table privilege.
- The role grants live in the last file of each base set, `V6.0__claimius_grants.sql`, and are applied on every build and every replay, so a function added later is granted with no consumer calling an internal function.
- Every audit partition holds exactly the grants of the audit table.
- A failing write of an organization or location records its audit error row under the first app it is linked to, and records none while it is linked to no app.
- Audit rows are written in the transaction of the change they record, on monthly partitions.
- A machine client's secret is verified with bcrypt once per credential; later requests compare a digest and reread the client for status and expiry.

### Apps and bootstrap

- `upsert_system_app` stamps every row it writes with the system user's grant, so every `sa_created_by` names a grant from the first row.
- `upsert_app_user` stamps the default grant of a first login with the acting grant a caller passes, or else with the new grant's own id, never with a user id.
- Every replay rewrites a `sa_created_by` a v1.1.9 set wrote as a user id to that user's grant where it is unambiguous, the user holding exactly one live grant in the row's app, and leaves every other stamp; `audit` keeps what it holds.
- `upsert_app` creates every app after the system app, owned by an organization and under the authority of a grant of another app: the app, its owner and default claims, their bindings and the grant to the actor, in one call.
- The first binding of a new app is accepted from an owner of the organization that owns the app, and the first binding on a new user from an owner of the organization the user was made a member of, so `upsert_app` and `insert_organization_user` work before the new app or the new user carries any binding.
- `upsert_app_client` is idempotent: a replay adds the client's binding and its capability grant only when a live one is missing, so a seed that calls it can run again on an upgraded database.

### Graphs

- Both graphs and both link graphs take a window: at most a given number of children of each type per parent, in name or usage order, continuing after a given node. `GraphWindow` is exported from `disciple/sdb`.
- A windowed link graph returns `node_ids` beside `links`, the ids of every node the window keeps, the graph's roots and start among them, so a node that keeps no child and so has no link still reaches the consumer's object set.
- The cached claim graph is validated against the snapshot it was built under, so a grant committed during the build is never missed.

### Federation

Prophets now federate. A prophet mirrors an app of a peer prophet, each app has one home that decides its writes, a mirrored record whose id collides is refused and recorded instead of merged, and an app's home moves only through a handover the new home accepts. A write sent to a prophet that is not the app's home answers `409` with the home in `SAuth-Home`. A hybrid is now a prophet mirroring one app of a peer.

## Adopting version 2

Each consumer makes these changes. Every item marked **breaking** fails to build or behaves differently until it is made.

| Change | What to do |
|---|---|
| **breaking** Listing pages | `GetOrganizations`, `GetLocations`, `GetSecrets` and their `...Query` forms take `after *uuid.UUID, limit int`; pass `nil, 0` for the whole range, or read both from `?cursor=&limit=` with `QueryPage` |
| **breaking** Listing filter | `ObjectWhere(q, actor, objectType, required, objectID, after, limit)` takes the select query and returns it filtered, instead of returning a predicate string, and orders it by id only when `after` or `limit` is set; an unpaged listing that needs an order sets its own. A query without a model names its table with `Table` or `TableExpr` |
| **breaking** Graph window | `GetOwnerGraph`, `GetClaimGraph` and their `...Query` forms take a `GraphWindow{Width, Sort, NextID}`; the zero value returns the whole graph |
| **breaking** Link graphs | `get_graph_links_owner` and `get_graph_links_claim` take `p_width`, `p_sort` and `p_next_id` after `p_depth`, and their old signatures are dropped; a call by position or by name resolves through the defaults, a reference by signature, such as a `GRANT`, names the new one |
| **breaking** Usage | `Usage.Add(appID *uuid.UUID, userID, objectType, objectID)` takes the app first; pass `nil` for the deployment's own app |
| **breaking** App creation | Create every app after the system app with `claimius.upsert_app(p_actor_user_claim_id, p_slug, p_name, p_org_id, p_private_key, p_private_seed, ...)` instead of inserting `samna_app`, `prophet_state` and the claims by hand; the actor holds owner on `p_org_id` in its own app |
| **breaking** Role grants | Remove every call to `_grant_prophet_roles` or `_grant_disciple_roles`; the base set applies them on every replay, and no consumer calls a `_grant_*` function |
| **breaking** Module path | Import `github.com/nimling/samna-auth-middleware/v2/...` everywhere and `go get github.com/nimling/samna-auth-middleware/v2@<tag>`; the path without `/v2` ends at v1.1.9 |
| **breaking** Table tags | Qualify every model's tag as `bun:"table:schema.name"`: `ObjectTypeOf` reads the tag as written and a consumer's types pass through untouched; `ObjectType.Validate` is the opt in check |
| **breaking** Sync cursor | The cursor and the `SAuth-Seq` header are `<txid>.<seq>`; `WaitForSeq` takes a `client.SyncCursor`, the value a routed write returns from `Seq()` |
| **breaking** Audit | `WriteAudit(ctx, idb, appID, ...)` and `sdb.Write(ctx, idb, ...)` take the transaction of the change and return an error |
| **breaking** Masks | Review claims whose bindings carry a mask meant to add bits, and denies meant to leave dependent bits standing |
| **breaking** Hybrid | `upsert_prophet_peer` takes the upstream prophet, its endpoint and the mirrored app's slug and secret; `get_disciple_app` raises on a hybrid, so use `get_app_id` |
| Bindings on own rows | Bind a claim on a row of the consumer's own table with `NewInsert().Model(&ClaimObject{...}).Access(ac)`, which a disciple sends to the prophet, instead of a local `claimius.insert_claim_object`, which only the disciple ever holds; bookable does the latter in 10 handlers, `PostBookableType` among them. The actor must hold on the binding's owning organization what the binding hands out |
| First login | `upsert_app_user` takes `p_sa_created_by UUID DEFAULT NULL` last; pass the acting grant when a caller grants the default claim on a user's behalf. A call by position or by name resolves through the default, a reference by signature, such as a `GRANT`, names the new one |
| Schema ref | Move the `ref` of the claimius git include to the tag `go.mod` pins, and drop in the consumer's own `V2.0.0__claimius_unified.sql` whatever of its own it made for the earlier line |

The operator then runs, against every live database of the consumer:

```sh
smig upgrade
smig rebase --prune="Claimius Migrations"
smig up
```

`smig upgrade` lets the ledger accept the new tool version, the rebase folds the applied rows of the `Claimius Migrations` step, whose files the middleware no longer ships, so `up` does not abort on them, and `smig up` applies the base sets and the consumer's own migration. The prune names its step: a bare `--prune` also mirrors every other file into the ledger as applied, so `up` would skip the new base sets.
