A disciple whose sign in callback failed used to send the browser straight back into the flow, and the prophet, still holding a live session, issued a new code at once, so the browser looped between the two. This release makes a failed callback answer as RFC 6749 and OpenID Connect Core describe: the failure is named, the flow cookies are cleared, and the next attempt asks the prophet for a fresh authentication instead of reusing its session.

## A failed sign in callback answers an OAuth error

When the callback cannot complete, the disciple clears every cookie it set for the flow, the state, the verifier, the cli target, the return path and the session cookies, logs the cause with its OAuth error code, and redirects the browser once to its own `/api/auth/login` with `prompt=login`, `error` and `error_description` as query parameters. The login forwards all three to the prophet's authorize request, and `prompt=login` makes the prophet ignore its session and ask the person to sign in again.

| Failure | `error` | Description |
|---|---|---|
| The prophet answered the authorize request with an error | the prophet's own code | the prophet's own description |
| The callback carries no authorization code | `invalid_request` | The sign in came back without an authorization code. |
| The state does not match the browser's cookie | `invalid_request` | The sign in state does not match this browser. |
| The browser holds no verifier | `invalid_request` | This browser holds no verifier for the sign in. |
| The prophet refused the code exchange | the prophet's own code, such as `invalid_grant` | the prophet's own description |
| The prophet could not be reached or answered a server error | `server_error` | The sign in could not be completed. |

- A `next` path carried in the state still travels with the retried login, so a successful retry lands where the person was going.
- A cli sign in with a foreign state is refused the same way and the code is never shown.
- The login passes `prompt`, `error` and `error_description` through only when they are present; a plain login sends the authorize request it always did, the cli parameters included.
- The TypeScript package is unchanged: nothing a browser calls has a new shape.

## The retry guard

The first failure within a minute redirects to the login. A second failure in the same browser within that minute answers `400` with an html page naming the error and its description, with a sign out link and no redirect, so no loop is possible. The guard is the cookie `sauth_login_retry`, which lives for sixty seconds and is cleared by a callback that completes.

## Retention on a mirrored app

The hourly retention run on a prophet leaves the access codes of an app whose home is another prophet to that prophet. A prophet mirroring a peer's app completes its retention run instead of stopping on the codes it does not decide.

## Grants restored on a replay

Every function's execute grant and every view now sit in the baseline file that defines them, on both roles. A consumer that moves its pin and replays the baseline gets every grant and view back with the functions, so the reader and writer roles can call every function and read every view after the replay.
